# Web feature parity plan

`apps/web` (Next.js) is a new companion to `apps/mobile` (Expo), sharing the same Supabase project. This tracks what's built vs. outstanding on web, so feature/bugfix work can keep the two apps in lock-step (see the standing rule in `CLAUDE.md`). Update this file when you close a gap or find a new one.

## Built

- **Auth** — email/password sign in, sign up (with username), email-confirmation callback (`app/auth/callback`), sign out. Session managed via `@supabase/ssr` cookies + middleware refresh. Social sign-in scaffolding (Google/Apple buttons on `/login` and `/signup`, `supabase.auth.signInWithOAuth` redirect flow via a shared `signInWithProvider` Server Action in `lib/auth/socialActions.ts`, reusing the same `/auth/callback` route email confirmation already uses since it's provider-agnostic) — **not yet functional**, the providers aren't configured in the Supabase dashboard yet, so clicking these currently errors. Simpler than mobile's `expo-auth-session` custom-scheme + manual token-extraction flow, since web gets a plain redirect. Forgot/reset password (`/forgot-password`, `/reset-password`, linked from `/login`) — unlike every other web auth flow here, recovery links deliver tokens as a URL hash fragment rather than a `?code=` param, so `/reset-password` can't reuse `/auth/callback`'s server-side exchange and instead parses `window.location.hash` client-side (`ResetPasswordForm`) and calls the browser client's `setSession()` directly, mirroring mobile's `useAuthDeepLinks` approach for the same reason (no server-visible callback for this particular flow).
- **Games — list, detail & creation** — upcoming/past games list (`app/(protected)/games`), respecting the same visibility rule as mobile (visible once `visible_at` passes, or always visible to the game's admin). Game detail page with capacity/waitlist display and sign up / withdraw (Server Actions), using `@temur/shared`'s `getGameCapacity`/`getActivePlayers`/`getWaitlistPlayers`/`getNextSignupOrder`/`getPlayerDisplayName`. Create game (`games/new`, optional `?group=<id>` preset from a group's detail page): friends-invite or group mode, default kickoff defaults to the next Saturday not already taken (mirrors mobile's clash-avoidance loop), visible-from date, players-per-team, team names; friends mode sends `game_invite` pushes on create, same as mobile.
- **Results & ratings** — result entry (score or win/draw/loss outcome, `games/[id]/result`) via the `set_game_result` RPC — open to anyone who can view the game, not admin-gated, same as the RPC's own authorization; player ratings 1–10 (own ratings private) via `player_ratings` upsert, aggregate averages on the game detail page's player rows via `get_player_rating_summary`. Entry point only shown once the game's kickoff has passed, matching mobile.
- **Ringers** — on the game detail page (group games only): admin "Open to Ringers" (sends a `ringers_open` push to every group member, mirrors `notifyGroupMembersRingersOpen`), any group member can then "Add a Ringer" with saved-name quick-picks until kickoff, ringer badge + remove button (adder or admin) on player rows. Saved-ringer management (`/friends/ringers`, linked from the Friends page) — add/list/delete names for quick re-add, mirrors mobile's `RingersScreen`.
- **Team assignment board** — `games/[id]/team-assignment` (admin only, linked from game detail once someone's signed up). List view (per-player T1/T2 buttons) and a full drag-and-drop board view built on `@dnd-kit/core` (mobile's `PanResponder`-based board has no web equivalent) — three drop zones (unassigned pool, team 1, team 2), free-form position within a team box saved as normalized `board_x`/`board_y`, same data model as mobile. Auto-assign (alternate) and clear-all. The state-transition logic (`teamAssignmentState.ts`) and drag geometry (`boardGeometry.ts`, position normalization + the grid fallback for players without a saved position) are pure functions with full Jest unit test coverage — `apps/web` now has a test runner (`ts-jest`, `npm test -w apps/web`) for the first time, set up as part of this feature.
- **Profile** — view (`app/(protected)/profile`), edit display name/username/avatar (`profile/edit`, avatar via `<input type="file">` uploaded directly to the `avatars` Storage bucket, owner-write RLS already in place), change password (`profile/change-password`, email-auth users only), notification preferences (`profile/notifications`, see Notifications below), About screen (`profile/about` — version from `apps/web/package.json`, build from `VERCEL_GIT_COMMIT_SHA` when deployed, GitHub link). Uses `@temur/shared`'s `validateUsername`/`formatUsername`/`getInitials` (new — extracted from mobile's duplicated initials logic).
- **Theme toggle** — explicit light/dark/system control on the Profile page (mobile's `ThemeContext` equivalent). Unlike mobile's `AsyncStorage`, web persists the choice in a `theme` cookie (`lib/theme.ts`) read server-side in the root layout, which stamps `data-theme` on `<html>` before first paint — no flash, no client-only theme hook. `globals.css`'s dark-mode tokens are guarded so an explicit `data-theme="light"`/`"dark"` overrides the `prefers-color-scheme` media query when set, and "system" (the default, no cookie) falls back to it. Reading the cookie in the root layout makes every page dynamically rendered (previously-static pages like `/login` lost static optimization) — an accepted tradeoff for a per-user preference that needs to apply before paint.
- **Friends** — friends list with remove (`app/(protected)/friends`), search + send request (`friends/search`, debounced client-side search calling a Server Action directly), accept/decline incoming requests (`friends/requests`). Sends a `send-notification` push on new request, same as mobile (no-op for users without a push token, so this works even though web itself has no push story yet). Uses `@temur/shared`'s `getInitials`.
- **Groups** — list with pending-invite banner and create group (`app/(protected)/groups`, `groups/new`), group detail with inline admin edit (name/description/team-assignment message template), "Create Game" and leave group (`groups/[id]`), member list with promote/demote/remove (`groups/[id]/members`), invite a friend to the group (`groups/[id]/invite`, admin only) and view/accept/decline incoming group invitations (`groups/invites`), group's upcoming-games list (`groups/[id]/games`). `Group`/`GroupMember(WithProfile)`/`GroupWithRole`/`GroupInvitation(WithDetails)` types moved from mobile-only `types/group.ts` into `@temur/shared` since both apps need them now.
- **Notifications** — web has no push registration (not a native app), so instead of Web Push/VAPID/service worker, went with realtime in-app badges (see above) plus email as the out-of-band channel, matching every event mobile pushes for (`friend_request`, `friend_accepted`, `group_invite`, `game_invite`, `team_assigned`, `ringers_open`, `game_visible`). `send-notification` and `sweep-visible-games` send push and email as two independent delivery paths — a recipient with no `push_token` (every web-only user) still gets email; a mobile user with a token gets both. Email sent via Resend's REST API (`supabase/functions/_shared/email.ts`, no SDK, same plain-fetch approach as the existing Expo push calls) — needs `RESEND_API_KEY` (and optionally `RESEND_FROM_EMAIL`, `PUBLIC_SITE_URL`) provisioned via `supabase secrets set` on the remote project; without it, email is skipped gracefully and push is unaffected. Reuses each call site's existing `title`/`body` copy rather than a third parallel template system. Per-type, per-channel preferences (`profile/notifications`) let a user pick push/email independently for each event type, with a "select all" per channel — replacing the old single `notifications_enabled` toggle; see the Notifications bullet in the root `CLAUDE.md` for the schema and merge-defaults details.

## Outstanding

Each item below references the mobile implementation to mirror (screens/hooks/services under `apps/mobile/src/`).

### Social sign-in — provider configuration
- Code is in (see Built above); the Google and Apple OAuth apps/credentials still need to be set up in the Supabase dashboard (Auth → Providers) before the buttons will actually work. Not something this repo can do — needs whoever holds the Supabase project's dashboard access.

### Cross-cutting: realtime updates
- Mobile subscribes to `postgres_changes` (games, player_games, friendships, group_invitations, game_invitations, groups, group_members) to live-update lists and tab badge counts. Web's pages are otherwise plain Server Components that only refresh on navigation/`revalidatePath` after a mutation.
- **Built**: Friends/Groups nav badge counts (`app/(protected)/RealtimeBadge.tsx`, mirrors mobile's `MainNavigator` badges) — a reusable client component parameterized by table/channel/filters, subscribing via `postgres_changes` and refetching an exact count. Wired into `(protected)/layout.tsx` with an SSR-provided `initialCount` for first paint.
- Two real bugs found and fixed while building this (both affect mobile too, or would affect any future web realtime work):
  - **No migration ever added any table to the `supabase_realtime` publication.** Realtime "worked" on the remote project only because someone manually toggled replication on via the Dashboard — unmigrated, unreproducible, silently broken on the local stack / any fresh project. Fixed in `supabase/migrations/20260819000000_add_realtime_publication.sql`, which also sets `REPLICA IDENTITY FULL` on the same tables (the default, primary-key-only identity means UPDATE/DELETE payloads don't carry the non-PK columns most RLS SELECT policies filter on, silently dropping those events).
  - **`RealtimeBadge`'s subscribe callback needs to explicitly call `supabase.realtime.setAuth(session.access_token)` before subscribing.** `@supabase/ssr`'s `createBrowserClient()` doesn't automatically thread the cookie-backed session's JWT onto the realtime socket the way plain `createClient()` does — without it, the socket connects with only the anon key, RLS evaluates `auth.uid()` as NULL, and every event is silently dropped (no error). This is `@supabase/ssr`-specific; mobile's plain `createClient()` isn't affected. Also refetch on the subscribe callback's `'SUBSCRIBED'` status (not just on future events), so a change landing in the connect/reconnect window isn't missed forever.
- Remaining: per-screen live list refreshes (games list, game detail, group detail, etc. — mobile's other 7 local subscriptions) are still request-time-freshness only on web. Decide per-feature whether that's worth adding — start where it's actually missed, don't blanket-apply.
